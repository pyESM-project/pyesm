Fill exogenous model data
=========================

Among the whole CVXlab modeling process, this is the most *time-consuming* and 
*errors-prone* step, especially for large models. Numerical data for *exogenous 
Data Tables* are provieded by the user into the *blank Excel file(s)* generated 
in the :ref:`previous step <data-structures-init>` and stored in the 
``<model_dir_name>/input_data`` directory by default.

As for Sets coordinates, **Excel** has been chosen as the sole data input format, 
due to the fact that large amount of data need to be entered and manipulated: 
relying on Excel allows to easily visualize, filter and manage the data.

Depending on the user's preference defined at the :ref:`generation of the Model 
class <generate-model-class-instance>`, *two options* are possible:

- **Single Excel data input file**: all numerical data are filled in a single 
  Excel file, named as ``input_data.xlsx`` by default (naming conventions defined in 
  :py:attr:`default module <cvxlab.defaults.Defaults.ConfigFiles>`), where *tabs 
  are named as exogenous Data Table names*. This is the default option when the 
  Model class is generated (``multiple_input_files=False``).
- **Multiple Excel data input files**: each exogenous Data Table is defined as 
  a separate Excel file named ``<data_table_name>.xlsx``, with a unique tab defined 
  as ``<data_table_name>``. This results in case Model class is generated with 
  ``multiple_input_files=True`` argument. This option is preferable in case of 
  several Data Tables with large amount of data.



Generic file tab structure
--------------------------

Each Excel file tab (either the single one or each of the multiple files) is 
structured as a *normalized* table, defined as a *long format* table, where each 
row corresponds to a specific combination of coordinates of the Data Table, and 
the numerical value is reported in a single final column. 


.. list-table:: Generic structure of each tab in input data XLSX file.
   :header-rows: 1
   :widths: 5 20 10 10

   * - <id>
     - <set_key_#>_Name
     - ...
     - values

   * - <int>
     - <str>
     - <str>
     - <int | float>


.. rubric:: Fields description

- ``<id>`` column is a unique identifier for each row in the table. It identifies 
  the specific coordinate combination of the Data Table, and it is the same key 
  used in the SQLite database. It is automatically generated by CVXlab when the 
  blank Excel file(s) are generated, and it should not be modified by the user.
- ``<set_key_#>_Name`` columns correspond to the names of all the Sets defining  
  the coordinates of the Data Table. Entries in these columns are expressions of the 
  **domain** of the Data Table: total number of rows correspond to the *Cartesian 
  product of all the Sets coordinates of the Data Table*. These columns are 
  automatically generated by CVXlab when the blank Excel file(s) are generated, 
  and should not be modified by the user.
- ``values`` column corresponds to the numerical values of the Data Table, and 
  *it is the only column that should be filled by the user*. It can contain either 
  integer or float values, depending on the specific Data Table definition.

  
Notes
-----

- Before start filling the data, it is recommended to *carefully revise the model 
  structure* (i.e., Sets, related filters, definition of Data Tables, etc.). Indeed, 
  every structural model change (such as, changing Sets coordinates or adding 
  coordinates filters categories) will require all data structures, including Excel 
  input data file(s), to be re-generated from scratch.
- When data structures are :ref:`initialized <data-structures-init>`, Excel blank 
  files are generated. In case of *pre-existing version of such files*, already be 
  filled with data by the user, CVXlab prompts the user to choose whether to overwrite 
  the existing file (and thus lose all the data already filled) or to keep it. 
  It is suggested to keep a backup copy of the filled Excel file(s) before 
  initializing data structures, to avoid losing data in case of accidental overwrite.
